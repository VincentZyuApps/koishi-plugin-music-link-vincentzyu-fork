# music-link 日志系统重构规划

- 日期：2026-08-01
- 状态：日志业务代码已实施并完成代码验收
- 目标：统一生产日志入口，形成常驻 INFO 与可选 DEBUG 两档日志
- 约束：本文不超过 500 行

## 1. 本次重构范围

本次重构覆盖 `lib/` 下全部生产日志，包括 `logger.*`、`ctx.logger.*`、旧 `logInfo()` 和直接 `console.*` 喵。

测试脚本自身的 `console.*` 不属于生产日志，可以继续保留喵。

`md-tryer-vincentzyu-fork` 不属于这个仓库的日志重构范围，它仍按自己的规则在发送失败时始终输出完整诊断喵。

本次只调整日志输出和相关依赖注入，不改变搜索、选歌、下载、渲染、缓存或消息发送行为喵。

## 2. 已确认的最终原则

1. 插件只提供 `logInfo()` 与 `logDebug()` 两个日志函数喵。
2. 两个函数底层都只调用 `ctx.logger.info()` 喵。
3. 插件不再调用 `ctx.logger.warn()`、`ctx.logger.error()` 或 `ctx.logger.debug()` 喵。
4. 插件不再直接调用 `console.log/warn/error/debug()` 喵。
5. `logInfo(summary, detail)` 始终输出，并将两个参数合成同一条日志喵。
6. `logDebug(message, data)` 仅在 `verboseConsoleLog=true` 时输出，并形成独立日志喵。
7. `verboseConsoleLog` 只控制 `logDebug()`，不能隐藏任何失败摘要喵。
8. 警告和错误通过 `⚠️`、`❌` 表达，Koishi 底层等级仍然是 INFO 喵。
9. 删除旧 `config.loggerinfo` 兼容读取，只保留 `verboseConsoleLog` 喵。
10. `verboseFileLog` 与 `verboseConsoleLog` 保持完全独立喵。
11. 每个插件实例创建自己的日志工具，不使用 global 或模块级共享 Logger 喵。
12. 所有模块一次迁移到最终分类，不保留半完成的中间日志体系喵。
13. 两档日志分别统一使用 `[🎵 INFO] <语义 emoji> <主题>` 与 `[🐛 DEBUG] <语义 emoji> <主题>` 前缀喵。

这套设计主动放弃 Koishi 按 WARN/ERROR 等级过滤和着色的能力，换取插件内部只有两档、行为稳定且不受全局 DEBUG 等级二次过滤的日志模型喵。

## 3. 目标 API

### 3.1 文件位置与创建方式

新建 `lib/util/logger.js`，并只在 `apply(ctx, config)` 中创建一次实例级日志工具喵。

```js
const musicLogger = createMusicLogger(ctx, config)
const { logInfo, logDebug } = musicLogger
```

下游模块统一接收 `musicLogger`，不再同时传递 `logger` 与 `logInfo`，业务所需的 `config` 仍正常传递，废弃占位参数全部删除喵。

```js
registerMiddleware(ctx, config, musicLogger)
registerCommand6(ctx, config, musicLogger, sharedFunctions)
registerCommand9(ctx, config, musicLogger, sharedFunctions)
```

### 3.2 `logInfo(summary, detail)`

`logInfo()` 表示常驻业务摘要，无论 `verboseConsoleLog` 是否开启都输出喵。

```js
logInfo('🎼 聚合搜索完成', '网易云 20 首，QQ 20 首，酷狗 20 首，总计 60 首')
```

底层只执行一次喵：

```js
ctx.logger.info('[🎵 INFO] 🎼 聚合搜索完成 | 网易云 20 首，QQ 20 首，酷狗 20 首，总计 60 首')
```

具体规则如下喵：

- `summary` 必须是简短、独立可理解的字符串喵。
- INFO 前缀固定为 `[🎵 INFO]`，其后必须跟一个语义 emoji 和主题喵。
- summary 没有显式 emoji 时，由 logger 根据主题自动选择，无法判断时使用 `📝` 喵。
- `detail` 可省略，存在时使用 ` | ` 与 summary 连接喵。
- `detail` 只接受适合单行展示的字符串、数字或布尔值喵。
- 对象、数组、原始响应和多行文本不能放入 `logInfo()` 喵。
- 原始 Error 不能直接传入 `logInfo()`，应先通过摘要函数提取名称、消息、状态码和必要业务码喵。
- 一次业务事件原则上只产生一条 `logInfo()`，不再用树状多行日志拼接同一事件喵。

### 3.3 `logDebug(message, data)`

`logDebug()` 表示详细诊断，仅在 `config.verboseConsoleLog === true` 时输出喵。

```js
logDebug('QQ RichUI 失败诊断', () => ({
    request,
    response,
    stack: error.stack,
}))
```

详细模式下仍通过 INFO 输出喵：

```text
[I] music-link [🐛 DEBUG] 💥 QQ RichUI 失败诊断
{
  "request": {},
  "response": {},
  "stack": "HTTPError: Bad Request ..."
}
```

具体规则如下喵：

- `message` 是简短的诊断主题喵。
- `data` 可以是字符串、Error、对象、数组或返回这些内容的函数喵。
- 函数形式是推荐写法，详细模式关闭时不能执行函数或进行序列化喵。
- message 与格式化后的 data 组成一条独立的 `ctx.logger.info()` 调用喵。
- message 没有显式 emoji 时，由 logger 根据主题自动选择语义 emoji，无法判断时使用 `🔍` 喵。
- 多行 JSON 和 Stack trace 保持可读缩进，不强行压缩成一行喵。
- 格式化失败不能影响原业务，也不能让日志函数向外抛错喵。

### 3.4 警告与错误

不创建 `logWarn()` 或 `logError()`，也不直接调用 Koishi 的 WARN/ERROR 方法喵。

可恢复失败、已执行降级或只影响部分字段时，用带 `⚠️` 的 `logInfo()` 喵。

当前命令整体失败、关键能力不可用或配置导致功能无法继续时，用带 `❌` 的 `logInfo()` 喵。

完整 Error、请求 payload、原始响应和 Stack trace 放在紧邻的 `logDebug()` 中喵。

```js
logInfo(
    '⚠️ QQ RichUI 发送失败，已回退普通歌曲字段',
    summarizeQqError(error),
)
logDebug('QQ RichUI 失败诊断', () => buildQqDiagnostics(error, request))
```

关闭详细模式时仍能看到结果和下一步，开启后才增加足够定位问题的上下文喵。

### 3.5 状态标记规范

| 标记 | 含义 | 示例 |
| --- | --- | --- |
| `[🎵 INFO]` | 常驻业务摘要前缀 | 其后继续跟 `✅/⚠️/❌/🔎` 等语义 emoji |
| `✅` | 成功完成的重要结果 | 文件发送成功、渲染结果发送成功 |
| `⚠️` | 可恢复异常、降级或部分失败 | RichUI 失败后回退、单平台搜索失败 |
| `❌` | 当前操作最终失败或关键配置错误 | 下载最终失败、缓存目录不可用 |
| `⏳` | 值得用户关注的长耗时状态 | 大文件下载超过提示阈值 |
| `[🐛 DEBUG]` + 语义 emoji | 仅详细模式出现的诊断信息 | `🌐` 请求、`📁` 路径、`⏱️` 计时、`💥` 异常 |

其他业务图标可以保留，但不能代替 `⚠️` 与 `❌` 的异常语义喵。

## 4. 格式化、安全与性能

### 4.1 安全格式化

`lib/util/logger.js` 提供统一的单行格式化与详细数据序列化喵。

- 支持 Error、BigInt、Headers、Buffer、循环引用和不可枚举 Error 字段喵。
- Error 详细格式包含 name、message、stack、cause、HTTP status 和 response data 喵。
- 循环引用显示为 `[Circular]`，不能导致二次异常喵。
- Buffer、ArrayBuffer、Base64 和大型二进制正文只记录类型与长度，不倾倒内容喵。
- QQ payload 和响应 JSON 保留完整结构，但先执行敏感字段过滤喵。
- 歌单完整数据继续写文件，不通过控制台详细日志整体倾倒喵。

### 4.2 敏感信息

以下键名及常见大小写、下划线变体必须脱敏喵：

- `authorization`、`cookie`、`set-cookie` 喵。
- `token`、`access_token`、`refresh_token` 喵。
- `secret`、`client_secret`、`bot_secret` 喵。
- 明确属于认证用途的签名、ticket、session key 喵。

URL 中的普通歌曲 ID、关键词和音质参数可以在详细模式显示，认证参数必须脱敏喵。

### 4.3 性能边界

- 关闭详细模式时，lazy data 回调执行次数必须为零喵。
- 不能为了生成日志重复解析响应、重复构造 RichUI payload 或复制大型歌单喵。
- 常驻摘要应复用业务流程已经计算出的名称、数量、平台和耗时喵。
- 日志格式化器本身失败时使用短回退文本，原业务继续执行喵。

## 5. 常驻日志分类

关闭 `verboseConsoleLog` 后，只保留能说明业务状态、最终结果、降级动作或可执行错误的日志喵。

### 5.1 启动与配置

- 插件版本、渲染顺序和严格/并行模式合并为一条启动摘要喵。
- 启用的命令名称合并为一条配置摘要喵。
- 资源缺失后开始下载、下载成功和最终失败保留喵。
- 无效配置回退到默认值时使用 `⚠️` 摘要喵。
- 导致对应功能不可用的配置错误使用 `❌` 摘要喵。

### 5.2 命令、搜索与选歌

- 命令开始时记录命令类型、关键词或 ID 模式喵。
- 聚合搜索开始时记录关键词、平台和每平台数量喵。
- 聚合搜索完成时记录各平台数量和总数喵。
- 最终选歌时记录歌曲名、歌手、平台、音质和时长喵。
- 音质不可用并切换下一档时使用 `⚠️` 摘要喵。
- 单个平台搜索失败但聚合继续时使用 `⚠️` 摘要喵。
- 命令最终失败时使用 `❌` 摘要喵。

正常的一次搜索点歌应控制在大约 4 至 8 条常驻日志内，只有下载、降级或失败时才增加对应摘要喵。

### 5.3 下载与文件

- 下载开始时记录歌曲名、歌手和平台喵。
- 下载超过提示阈值时最多输出一次 `⏳` 提示喵。
- 下载完成时记录耗时和文件大小喵。
- 文件保存成功时记录文件名，不默认记录绝对路径喵。
- QQ 文件上传和发送完成时记录文件名喵。
- 模板命名失败并回退时使用 `⚠️` 摘要喵。
- 下载、上传或发送最终失败时使用 `❌` 摘要喵。

### 5.4 渲染与消息发送

- 最终采用的渲染模式成功发送时输出一条 `✅` 摘要喵。
- 渲染器不可用并切换下一种模式时使用 `⚠️` 摘要喵。
- 图文组合失败并拆分重试时使用 `⚠️` 摘要喵。
- 媒体音质降级、重试和最终跳过保留结果摘要喵。
- OneBot 卡片、QQ RichUI、QQ Markdown 或 Telegram 发送失败时记录失败结果和后续动作喵。
- 状态提示或撤回失败但不影响主体结果时只输出一条 `⚠️` 摘要喵。

### 5.5 中间件

- 成功识别匹配的音乐卡片时记录平台和卡片类型喵。
- 确定执行命令时记录命令名称和默认歌曲序号喵。
- 关键字段缺失、配置错误或中间件最终异常时记录 `❌` 摘要喵。
- 被白名单过滤的普通卡片不进入常驻日志喵。

## 6. 详细日志分类

以下内容仅通过 `logDebug()` 输出喵。

### 6.3 下载与文件过程

## 7. `verboseFileLog` 的独立语义

`verboseFileLog=true` 只负责把最后一次完整歌单写入 `log/songlist-latest.json` 喵。

写入成功后通过 `logInfo()` 输出一条歌曲数量和文件位置摘要，因为这是用户主动开启的文件功能结果喵。

即使同时开启 `verboseConsoleLog`，也不把完整歌单再次倾倒到控制台喵。

写入失败时通过 `logInfo('❌ ...')` 始终输出短摘要，通过相邻 `logDebug()` 输出 Error 与 Stack trace 喵。

## 9. RichUI 目标输出

### 9.1 默认档

```text
[I] music-link [🎵 INFO] ⚠️ QQ RichUI 发送失败，已回退普通歌曲字段 | HTTP 400，QQ code=40034028，message=Bad Request，trace_id=xxxx
```

### 9.2 详细档

```text
[I] music-link [🎵 INFO] ⚠️ QQ RichUI 发送失败，已回退普通歌曲字段 | HTTP 400，QQ code=40034028，message=Bad Request，trace_id=xxxx
[I] music-link [🐛 DEBUG] 💥 QQ RichUI 失败诊断
请求目标: group/xxxx
请求 payload: {...}
响应原始 JSON: {...}
Stack trace: HTTPError: Bad Request ...
```

默认档足以确认失败位置与回退行为，详细档用于判断腾讯响应、适配器请求和插件 payload 是否一致喵。

## 10. 测试计划

### 10.1 logger 单元测试

- `verboseConsoleLog=false` 时 `logInfo()` 输出一条，`logDebug()` 输出零条喵。
- `verboseConsoleLog=true` 时 `logInfo()` 输出一条，`logDebug()` 额外输出一条喵。
- 两个函数底层调用的只能是 `ctx.logger.info()` 喵。
- summary 与 detail 始终位于同一条日志并使用 ` | ` 连接喵。
- lazy data 在关闭时不执行，开启时只执行一次喵。
- Error、循环对象、BigInt、Headers 和 Buffer 均可安全格式化喵。
- 敏感键值会被脱敏，普通诊断字段保持完整喵。
- 两个插件实例采用不同配置时互不影响喵。
- 格式化异常不能向业务调用方传播喵。

### 10.2 业务回归测试

- command6 的 ID 点歌和歌名搜索喵。
- command9 的单平台与多平台聚合搜索喵。
- 音质降级、媒体重试和最终失败喵。
- QQ RichUI、QQ Markdown、QQ 文件、OneBot 卡片和 Telegram 图文发送喵。
- 下载、命名、缓存和临时文件清理喵。
- Canvas、SVG、Puppeteer 与 Markdown 渲染顺序喵。
- OneBot 中间件白名单与 `middlewareDefaultSongIndex` 喵。
- `verboseFileLog` 单独开启、与 console verbose 同时开启及写入失败喵。

### 10.3 两档日志快照

为正常点歌、聚合搜索、RichUI 回退和下载失败各准备默认档与详细档快照喵。

快照重点确认常驻日志数量、事件顺序、异常标记、敏感字段和 Stack trace 开关行为喵。

### 10.4 静态验收

```powershell
rg -n "\bconsole\b" lib
rg -n "(ctx\.)?logger.*\.(info|warn|error|debug)" lib
rg -n "new Logger|Logger.*require|require.*Logger" lib
rg -n -i "loggerinfo" lib
```

第一、第三和第四条在生产代码中应无命中，第二条只允许命中 `lib/util/logger.js` 内的 `ctx.logger.info()` 喵。

## 12. 验收标准

- 全插件只有 `logInfo()` 和 `logDebug()` 两种生产日志入口喵。
- 两种入口最终都只调用当前实例的 `ctx.logger.info()` 喵。
- 默认档不出现 API URL、原始对象、payload、响应 JSON 或 Stack trace 喵。
- 默认档保留所有重要结果、降级动作和失败摘要喵。
- 详细档可以还原搜索、选歌、下载、渲染和发送的关键执行过程喵。
- `⚠️` 与 `❌` 在全部异常摘要中语义一致且便于扫描喵。
- INFO 必须符合 `[🎵 INFO] <语义 emoji> <主题>`，DEBUG 必须符合 `[🐛 DEBUG] <语义 emoji> <主题>` 格式喵。
- 生产代码不存在直接 console、WARN、ERROR 或 Koishi DEBUG 调用喵。
- `verboseConsoleLog` 是唯一的控制台详细日志开关喵。
- `verboseFileLog` 只控制完整歌单文件，不向控制台倾倒歌单喵。
- 不记录认证秘密或大型二进制正文喵。
- 不改变任何音乐业务结果、降级顺序或消息发送顺序喵。
- 所有新增测试和现有相关测试通过喵。

## 13. 本轮评审重点

1. 常驻 INFO 的业务节点是否仍然过多或过少喵？
2. 正常搜索点歌控制在约 4 至 8 条常驻日志是否合适喵？
3. 下载开始、完成和文件发送成功是否都应常驻喵？
4. 中间件识别卡片与执行命令是否都应常驻喵？
5. 已确认统一前缀为 `[🎵 INFO] <语义 emoji> <主题>` 与 `[🐛 DEBUG] <语义 emoji> <主题>`，例如 `[🎵 INFO] 🔎 聚合搜索开始`、`[🐛 DEBUG] 🌐 API 请求` 和 `[🐛 DEBUG] 💥 发送失败诊断` 喵。
6. 历史文档是否确认只补迁移提示，不改写旧版本内容喵？
